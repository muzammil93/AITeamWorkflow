## Technical Summary

Implement a small repository-native safety harness without changing application behavior:

1. A top-level `Makefile` exposes stable human-facing commands.
2. `scripts/check_python_syntax.py` compiles Python source in memory, avoiding generated bytecode and excluding caches, virtual environments, dependency trees, and generated output.
3. `scripts/check_workflow_transitions.py` models only the locked Orchestrator transitions needed by the F00 dry-run scenarios, validates dependency/single-active-feature invariants, and hashes the live release-state file before and after to prove it was not mutated.
4. `tests/test_development_safety.py` uses standard-library `unittest` to test the safety helpers, scenario set, rejection behavior, and release-state immutability.
5. `DEVELOPMENT_SAFETY.md` is the canonical operator contract for dependency setup, checks, migration isolation, shared-staging/production gates, Git evidence, and safe recovery.
6. `package.json` gains explicit `typecheck` and compatible lint command names only if required to make the frontend commands stable. No dependency or lockfile change is authorized unless the current locked toolchain cannot expose the required command.

The aggregate command must continue through every check so one early failure does not hide later baseline evidence, then exit non-zero if any check failed.

## Frontend Changes

No UI or runtime frontend behavior changes.

Expose these check boundaries:

* `make check-types` → locked TypeScript compiler with `--noEmit`.
* `make check-lint` → repository lint script.
* `make check-build` → production Next.js build.

If `next lint` proves incompatible with the locked Next.js version, use the smallest toolchain-compatible ESLint invocation already supported by installed dependencies. Do not install a broad test framework or suppress lint failures.

## Backend Changes

No Flask runtime behavior changes.

Add development-only Python scripts:

* Python syntax checker:
  * Walk only repository-owned `*.py` sources.
  * Exclude `.git`, `.next`, `.venv`, `venv`, `node_modules`, and `__pycache__`.
  * Read as UTF-8 and call Python `compile()` without writing `.pyc`.
  * Print every syntax failure and return non-zero if any fails.
* Workflow transition checker:
  * Define a minimal immutable transition graph matching the locked Orchestrator model.
  * Run named fixtures for standard success, QA-first success, QA-first delta, QA repair, reviewer repair, repair exhaustion, milestone gate, and reconciliation failure.
  * Assert invalid transitions fail.
  * Assert a dependency-locked feature cannot start.
  * Assert only one feature is active.
  * Read and hash, but never write, the live SaleAura release-state file.

Use only Python’s standard library.

## Authentication / Authorization Impact

## Security Considerations

* Never print environment variables, tokens, or connection strings.
* No check may silently connect to shared staging or production.
* No command may install dependencies implicitly.
* Workflow dry-runs must use in-memory fixtures and read-only hashing of live state.
* Migration instructions must validate RLS, grants, functions, and advisor/security output in an isolated target before shared staging.
* Production mutation remains prohibited without explicit CEO authorization.
* Recovery guidance must preserve user work and must not prescribe destructive reset or checkout.

## Error Handling

* Individual commands pass through their underlying exit status.
* The aggregate baseline prints a per-check summary, executes all checks, and exits non-zero if any failed.
* Missing executables or dependencies are reported as unavailable/failing with an actionable setup command.
* Syntax checker errors identify file and line.
* Workflow checker errors identify scenario and invalid transition/invariant.
* Documentation distinguishes a failing historical baseline from a defect introduced by F00.

## Testing Guidance

Developer:

* Run each named command separately and the aggregate command.
* Record tool versions and exact exit outcomes.
* Run `python3 -m unittest discover -s tests -p 'test_*.py'`.
* Confirm the release-state checksum is unchanged by workflow dry-run.
* Run `git diff --check` in both repositories.

QA:

* Rerun all F00 commands independently.
* Temporarily exercise negative cases only through temporary fixtures or command options; do not edit live state.
* Inspect that no application route, component, backend service, SQL, legal, deployment, or billing file changed.
* Verify check failures are surfaced and aggregate execution continues.

## Migration Validation and Recovery

`DEVELOPMENT_SAFETY.md` must require the following future migration sequence:

1. Create a feature-scoped additive migration; never edit a migration already applied to a shared environment.
2. Record target feature, base schema/migration-history reference, filename, SHA-256 checksum, affected objects, data assumptions, and forward-fix/recovery plan.
3. Start or reset a disposable local Supabase/PostgreSQL target reconstructed from the recorded baseline.
4. Apply the migration only to that disposable target.
5. Test repeatability where the migration is designed to be idempotent.
6. Validate constraints, backfills, RLS enabled state, policies, grants, function execution privileges, owner isolation, anonymous denial, and intended service-role success.
7. Capture schema diff, tests, and security/advisor results.
8. Obtain QA and Reviewer approval before requesting shared-staging authorization.
9. Before shared staging, verify environment identity, current migration history, backup/recovery readiness, checksum equality, and absence of drift.
10. Never apply production migrations without explicit CEO approval.

Rollback is not presumed safe after data mutation. Prefer a reviewed additive forward fix. Any down migration must be separately validated against representative data and explicitly authorized.

## Risks

* Locked frontend dependencies are initially absent, so installation may require approved network access before executable frontend evidence exists.
* Historical frontend errors may make type, lint, or build fail. F00 records them and does not absorb repairs owned by later features.
* The current lint alias may be framework-version-sensitive.
* Python 3.13 is locally available while the product target is 3.11; record the local version and treat later 3.11 CI/staging validation as remaining evidence.
* A hard-coded transition graph could drift from governance. Tests and documentation must name the source model and Reviewer must compare them.

## Out of Scope / Not Implemented

* Database migrations or environment mutation.
* CI hosting configuration.
* New dependencies or test frameworks.
* Deployment, billing, or legal changes.
* Changes to the locked AI Team roles or state model.
